# Coordinator and evaluator only · EAI-02 DEV design v1

**Question.** With equal written knowledge, does access to executable operations improve correctness or reduce engineering effort when building the same offline validator? The intervention is the offer of the module. Leaving it unused is a treatment outcome. The first pair is exploratory even if it exhibits a large difference.

## Assignment, budgets and freezes

1. Before either build, pin the spec, family notes, shared brief, exact module, this design and packet hashes. Record the common environment and model configuration (model revision, reasoning level, context allowance, sampling settings when exposed), role prompts, installed tools and resource counters. The first preparation commit can supply the material pins. A change gets a new version and both arms restart if already exposed. No builder or evaluator should be an author of this preparation or have participated in EAI-01.
2. Stage only the allowlisted input files. Run two fresh contexts with private unprivileged Linux workspaces, identical local Python/Git/shell tools and no network, connectors, peer access, cross-session memory or repository history. Mount each packet at the same neutral path, read-only. Use the same model/configuration and prompts. Randomly assign packet to builder slot with a recorded coin flip and run concurrently if possible. Keep the assignment with the coordinator. Record any unavoidable differences. Material asymmetry or prior exposure invalidates comparison. A sequential rerun by the same informed agent cannot stand in for independent builders.
3. Both arms get one 25-minute build turn (16 tool invocations) and one 10-minute self-review turn (8 invocations), with a $0 ceiling. Count individual tool invocations even when batched. Record subprocess commands separately. Active wall time runs from delivery of the prompt to submission, including local tool execution, excluding only coordinator outages recorded for both arms. Target the same 32,768-token context and 8,192-token output ceiling per turn. If the runtime exposes only fixed limits, record the actual common limits and any deviation before dispatch. If the model snapshot or material settings cannot be matched, label that limitation and withhold a causal comparison. If a cap is reached, snapshot the available work. A missing runnable delivery is an operational failure, not a low defect count. Repeat the same neutral self-review prompt in both arms. Each builder may use its own test feedback. There are no evaluator hints, shared fixes or post-freeze repairs.
4. Save hashes and file manifests of both first-pass and final submissions, including tests, supplied dependencies actually retained, transcripts/counters and environment identity. Final submissions are the comparison candidates. Keep first-pass results descriptive. Record actual overrides or human interventions. Freeze the candidate hashes, evaluator version, rules, selection plan, ceilings and falsifiers **before** any independent selection or generation of fresh cases. Store that dated freeze receipt separately from case material. Exposed builder tests, the worked example, EAI-01 artifacts and any debugging cases retain DEV status.
5. A future confirmation study would require separate authorization, fresh matched pairs, a fixed pair count and cross-pair analysis, and a prospective case-selection and stopping rule. Set those before construction in that study. Any later confirmation cases are selected independently only after the relevant implementations and evaluation rules are frozen. A rerun of the current pair, a reconstructed known failure or tuning against an evaluator remains DEV.

## Independent black-box evaluation design

This describes a future evaluator. The preparation package contains no hidden cases, instantiated inputs, case seeds or scoring harness.

* **Roles.** An independent curator receives the frozen public contract and this rulebook, holds neither build, cannot see builder tests and does not see arm assignment. A coordinator checks exposure and assigns opaque candidate IDs. A runner invokes both CLIs separately on identical copied fixtures using the same stable, unprivileged environment. A blinded adjudicator compares recorded outputs with expected outcomes before identities are revealed. Keep the first-pass and final snapshots, stdout, stderr, actual exit, timing and fixture hashes.
* **Family selection.** Use each of seven contract areas once as a primary sampling stratum: invocation and manifest availability, JSON/schema validity, entry/path identity and uniqueness, filesystem boundary and file kinds, byte digest correctness, missing/unreadable evidence, and ordered reports/aggregate verdict/exit. Cover the full public interface. Reserve four case slots per stratum, including a positive control where the rule admits one and at least one situation that exercises the rule's contrasting outcome. Assign each case one primary stratum before execution. Secondary labels can describe interactions. Lock the eligible pool, stratum assignments, positive/contrast labels and stable item IDs before drawing a random seed. Use the logged seed to sample one positive and one contrasting item without replacement where both apply, then fill the remaining slots uniformly without replacement from the same stratum. Target 28 cases total, with at most eight proposed per stratum. Freeze selected cases and truth labels before either build is run. Shared semantics and unavoidable primitive bytes may recur. Direct replays, trivially renamed whole fixtures and dependence on arm-specific details are ineligible. Before the draw, a separate exposure checker compares the pool with disclosed DEV fixtures and builder-test inventories, quarantines overlaps, and logs exclusions without sending builder details to the curator. If a stratum cannot be filled, record incomplete coverage and keep the comparison UNKNOWN.
* **Ground truth.** Curator records the intended file graph, exact file bytes, manifest bytes, effective access, expected ordered rows/fields and exit. Derive digests independently from fixture bytes using the standard library and cross-check using a second local digest utility. Use independent reader/access controls under the same user for filesystem cases. Determine the JSON/exit oracle from the spec, never from either candidate or its tests. Check observer sensitivity using separate evaluator calibration material. If boundary access cannot be distinguished by instrumented observations or a validated control, mark that property UNKNOWN. Agreement between programs is never the oracle.
* **Fair execution.** Run each case in its own restored sandbox with identical byte/mode layout. Randomize the opaque build's run order per case. Compare JSON semantically, preserving types, fields and row order. Treat duplicate output keys or malformed stdout as invalid output. Capture actual exit separately. Use a 5-second per-process ceiling on bounded fixtures (at most 1 MiB per file and 4 MiB total per case). A timeout of the candidate under a working control is an execution failure. A runner failure, ambiguous spec or unsupported environment is UNKNOWN for both. Log the reason before unblinding. No selective replacements after seeing output.
* **Budget.** Per pair allow 90 active evaluator minutes for construction, controls and execution, plus 15 human review minutes per candidate, with $0 spending. Each reviewer checks reproducibility, standalone execution, alignment with the contract, unresolved defects and the clarity of the repair handoff. Record time to disposition, including rereads. Counterbalance order when feasible. If the human reviewer can identify the arm from source, flag that assessment as unblinded. Unfinished review is censored; missing observations stay UNKNOWN.

## Measures and decision rules

| Measure | Observable unit |
|---|---|
| Distinct unresolved defect families (primary) | Compare each final build with the independent oracle. Map each failing observation to the smallest violated contract obligation with a shared behavioral cause. Count one family once across correlated cases. Record evidence for any split or merge before unblinding; disputed attribution yields a range and UNKNOWN if the decision could change. Report family IDs and case counts, including failures common to both. |
| Incorrect rejection of valid inputs | Count fully matching, supported manifests that fail to yield the specified VERIFIED/0 and rows, over all such controls. Also count INVALID_INPUT on well-formed manifests whose correct outcome is FAILED or UNAVAILABLE, separately. Report false VERIFIED and missing/incorrect row evidence separately. |
| Engineering effort | For both snapshots record active minutes, turns, tool invocations, shell commands, retries and output tokens when observable. Report budget exhaustion. Missing telemetry is UNKNOWN, never zero. |
| Adaptation friction | Record minutes spent interpreting family notes or the module, operation families considered/used/inapplicable, adapter lines and failed integration attempts with evidence. Distinguish timed events from self-reports. Compare common-history uptake in both arms. Correctly implementing a known instruction that the other arm omitted is a real benefit. |
| Human review burden | Same checklist and clock for both deliveries. Record minutes, questions, unresolved issues, interventions and whether the cap was reached. Separate one-time curator/packaging work from candidate review. |
| Retained complexity | Count nonblank, noncomment Python lines, source files and nonstandard dependencies separately for production, tests/adapters and retained supplied code. Count a given file once. Report whether the CLI requires supplied operations at runtime. |

**Absolute floors.** A qualifying build delivers an offline, standard-library CLI. It cannot claim VERIFIED for a mismatch, missing/unreadable evidence or invalid manifest, follow an entry symlink, or write to the input fixture. All eligible cases must emit parseable reports with verdict-consistent exit status, and all fully matching valid controls must be accepted. Verify properties with the controls above. An unobservable floor cannot support a favorable judgment.

**Proposed exploratory interpretation.** C has a correctness advantage for this pair if it clears every floor, has at least one fewer distinct unresolved family than B, and uses at most 10% more active build time and at most two additional human review minutes. C has an efficiency advantage if both meet the floors with identical defect-family coverage and no additional false rejections, and C takes at least 20% less active build time with no increase in tool invocations or human review time. Report implementation and test complexity alongside either result. Adding a runtime dependency or requiring the supplied module to run the standalone CLI fails the delivery floor. Other complexity increases remain explicit tradeoffs.

A floor violation in C, equal coverage without the stated efficiency gain, or worse coverage defeats the corresponding advantage for this pair. A quality gain outside its resource margin is a tradeoff. Missing measurements that could change the conclusion, broken isolation or an unreliable oracle give UNKNOWN. Publish null results and both arms' better cases. These thresholds are proposed DEV choices. No single pair can confirm a general benefit or select a standing procedure.
